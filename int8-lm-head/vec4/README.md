# INT8 LM Head vec4 — Qwen3-VL-8B / CUDA / vLLM

This directory is the **vec4 follow-up** to the existing V2 INT8 LM Head study.
It is a single-operator optimization study for `Qwen3-VL-8B-Instruct` on one RTX 3090:
a weight-only INT8 GEMV whose weight and activation loads are both vectorized in the final
version. It is **not** a whole-model speedup, a memory-saving result, or a lossless
quantization claim.

## At a glance

| Layer | Result | Scope |
|---|---|---|
| Operator | BF16 **2.2446 ms** → V2 **1.4591 ms** → vec4 **1.0396 ms**; BF16 / vec4 **2.159×** | LM Head `[151936, 4096]`, batch≈1, single-token decode, synthetic BF16-rounded activation |
| NCU | global-load instructions **39.05M → 9.88M**; LSU pipe **94.92% → 27.16%**; naïve char4 sectors **330.92M** vs ideal **97.54M**; final vec4 restores ideal; DRAM **882.34 GB/s** (**96.83%** sustained peak) | single-kernel probe, RTX 3090 GPU0 |
| Serving | BF16 pooled mean **25.5922 ms** → vec4 **24.7129 ms**; client-side approximate TPOT **−3.44%** | 32 measured ABBA requests, descriptive observation; no significance test was performed; no significant benefit is claimed |

The three layers are separate measurements. Do not multiply the operator ratio by the serving
change, and do not quote either as a whole-model result.

## A. Problem and background

The LM Head is the last decode projection:

```text
hidden [4096] -> logits [151936]
```

At batch≈1, single-token decode, this is a matrix–vector product. The BF16 LM Head weight is
`151936 × 4096 × 2 B ≈ 1.16 GiB`, read on every decode step. The immediate cost is therefore
**weight bytes read**, not arithmetic throughput.

This study uses **weight-only INT8** with **FP32 activation and FP32 accumulation**:

- one symmetric scale per output row;
- INT8 is used only for weight storage;
- the multiply–accumulate stays FP32;
- the kernel writes FP32, and the vLLM path casts the result to BF16;
- this is **not** W8A8 and **not** Tensor-Core INT8.

The BF16 LM Head weight remains resident. The INT8 tensor is an additional copy; this repository
does **not** claim peak-memory savings.

## B. Implementation and evolution

### V2 baseline

- 4 warps per block, 1 warp per output row;
- scalar `int8` weight load, FP32 activation load;
- warp-shuffle reduction;
- FP32 accumulation;
- `y[row] = sum * scales[row]`.

### Naïve char4 (failed experiment)

The first attempt loaded weights as `char4` to reduce global-load instruction count. It did reduce
instructions, but the activation access became a cross-lane stride pattern. Theoretical global
sectors rose from **97.54M** to **330.92M** (~3.39× ideal), and L1TEX wavefront utilization rose to
**99.18%**. The kernel did not improve; this is retained as a profiler-driven negative result.

### Final char4 + float4

The final kernel keeps both memory streams contiguous:

- weight: `char4` vector load;
- activation: `float4` vector load;
- `N % 128 == 0` and 16-byte alignment required for the vector path;
- otherwise falls back to the V2 scalar path;
- 1 warp per row, 4 warps per block;
- warp-shuffle reduction and FP32 accumulation;
- output FP32, then cast to BF16 in the plugin.

The important lesson is not “char4 is faster.” It is that reducing instruction count while
breaking coalescing can make a memory-bound kernel slower. The final version reduces instructions
**and** restores ideal sectors.

## D. NCU analysis

Source: [`ncu/ncu_key_metrics.json`](ncu/ncu_key_metrics.json). The raw `.ncu-rep` and per-kernel
CSV files are intentionally omitted from the public tree because their exported metadata includes
machine/process identifiers and they are large.

| Metric | V2 | naïve char4 | final char4+float4 |
|---|---:|---:|---:|
| global-load instructions | 39,047,552 | 24,461,696 | **9,875,840** |
| LSU pipe, % peak sustained | **94.92%** | 60.25% | **27.16%** |
| theoretical global sectors | **97,542,912** | **330,916,608** | **97,542,912** |
| ideal sectors | 97,542,912 | 97,542,912 | 97,542,912 |
| L1TEX wavefront, % | 47.61% | 99.18% | 31.79% |
| DRAM read | 623.398 MB | 622.982 MB | 623.256 MB |
| DRAM read bandwidth | 832.60 GB/s | 838.96 GB/s | **882.34 GB/s** |
| DRAM % peak sustained | 91.37% | 92.07% | **96.83%** |
| `lg_throttle` samples | 35,967 | 42,429 | **81** |
| `long_scoreboard` samples | 22,103 | 14,551 | 69,797 |

Interpretation:

1. **V2 coalescing was already close to ideal**: theoretical sectors equals ideal sectors at
   `97.54M`. The original problem was not a bad scalar coalescing pattern.
2. The real pressure was **LSU instruction pipe utilization ≈94.92%**. The kernel was issuing a
   large number of load instructions even though the DRAM traffic was already near ideal.
3. Naïve char4 reduced global-load instructions to `24.46M`, but broke activation access:
   sectors rose to `330.92M` (~3.39× ideal), L1TEX wavefront rose to `99.18%`, and performance did
   not improve.
4. Final char4+float4 restores ideal sectors (`97.54M`), cuts global-load instructions to
   `9.88M`, and drops LSU pipe utilization to `27.16%`.
5. DRAM read is essentially unchanged (`≈623 MB`), while DRAM read bandwidth rises to
   `882.34 GB/s` (`96.83%` sustained peak). `lg_throttle` drops from `35,967` to `81`;
   `long_scoreboard` rises, consistent with the bottleneck moving to real memory latency /
   dependency rather than LSU issue.

NCU replay duration is not the same measurement as the operator microbenchmark. Do not compare
NCU kernel duration directly with the `1.4591 / 1.0396 ms` figures.

## E. vLLM integration

The integration is a **plugin**, not a fork or an upstream vLLM change:

- entry point: `vllm.general_plugins`;
- patch target: `LogitsProcessor._apply_head`;
- eligibility gates include: CUDA tensor, BF16 hidden states, `shape[-1] == 4096`,
  `numel() == 4096`, weight shape `(151936, 4096)`, `tp_size == 1`, no embedding bias,
  `UnquantizedEmbeddingMethod`, compatible head dtype;
- any failed gate falls back to the original BF16 path;
- CUDA Graph + `torch.compile` is the serving path used in the 32-request experiment;
- logs show `Plugin registered`, `Quantized weights loaded`, `Graph capturing finished`, and
  `custom_forward=1280 fallback=5`.

The plugin is version-tied to vLLM **0.28.0** internals. It is a monkey patch, not an upstream
implementation. A vLLM upgrade can break it.

The public plugin resolves its default artifact relative to the plugin file:

```python
DEFAULT_ARTIFACT = Path(__file__).resolve().parent / "artifacts" / "lm_head_int8_rowwise.safetensors"
```

Set `INT8_LM_HEAD_ARTIFACT` to an absolute path in real use. The artifact is not distributed.

## F. Serving ABBA

Source: [`serving/results.csv`](serving/results.csv), with sanitized metadata in
[`serving/experiment.redacted.json`](serving/experiment.redacted.json) and
[`serving/summary.redacted.json`](serving/summary.redacted.json).

Design:

- stages: A1 BF16 → B1 vec4 → B2 vec4 → A2 BF16;
- 2 warmup + 8 measured per stage;
- **32 measured requests** total;
- vLLM **0.28.0**, single GPU0, `--tensor-parallel-size 1`, `--max-num-seqs 8`,
  `--max-num-batched-tokens 2048`;
- client streaming HTTP; approximate TPOT from content chunk arrival times;
- CUDA Graph capture confirmed in logs; plugin/custom path verified.

Results from the CSV, independently recomputed:

| Stage | Mode | n | Mean TPOT |
|---|---|---:|---:|
| A1 | BF16 | 8 | 25.137925 ms |
| B1 | vec4 | 8 | 24.692400 ms |
| B2 | vec4 | 8 | 24.733338 ms |
| A2 | BF16 | 8 | 26.046438 ms |

Pooled:

- BF16 mean: **25.59218125 ms**
- vec4 mean: **24.71286875 ms**
- change: **−3.435864%**
- speed ratio: **1.035581×**
- BF16 A1→A2 drift: **≈3.61%**

This is a **32-request ABBA descriptive client-side approximate TPOT** observation. **No
significance test was performed; no statistically significant benefit is claimed.** It is not a
stable end-to-end speedup and not evidence that the CUDA kernel alone caused the difference.
CUDA Graph + `torch.compile` are part of the measured path.

The older V2 96-request ABBA/BAAB result (`−4.14%`) is a **different experiment**. It must not be
compared directly with this 32-request result, added to it, or multiplied by the operator ratio.

## G. Relationship to V2

The V2 study in the parent directory remains the historical baseline:

- V2 operator runs: **1.229×–1.978×**, median of three repeats **≈1.303×**;
- V2 serving: **96-request ABBA/BAAB**, client approximate TPOT **≈−4.14%**;
- V2 has its own limitations and quality evaluation.

The vec4 follow-up is a new, separately archived experiment:

- **operator-level** BF16→vec4 **2.159×**;
- **32-request** serving approximate TPOT **−3.44%** (descriptive).

Do not:

- label 2.159× as whole-model or serving acceleration;
- add the scheduler result and the kernel serving result;
- compare the vec4 32-request result with the V2 96-request result as if they were one series;
- claim memory savings, lossless quantization, statistical significance, or upstream merge.

## H. Reproduction and limitations

The public materials are **not a turnkey reproduction package**. Model weights, the quantized
artifact, the raw NCU captures, and the private stage logs are not included. No command in this
section was executed during public-repo preparation; only static path/command checks were
performed.

### H.0 Prerequisites

Use a Linux host with:

- an NVIDIA RTX 3090 (the benchmark checks for `3090` in the device name), a CUDA toolkit, and a
  working PyTorch build;
- Python 3.12.14 and PyTorch 2.13.0+cu129 (the recorded experiment environment);
- `safetensors` and `requests`;
- vLLM **0.28.0** in the same Python environment (the plugin uses vLLM 0.28.0 internals; it is
  not a general upstream plugin);
- `Qwen3-VL-8B-Instruct` weights and the INT8 artifact,
  `lm_head_int8_rowwise.safetensors`, supplied separately.

`serving/setup.py` installs the plugin module only. It does not install PyTorch, vLLM,
`safetensors`, or `requests`.

The commands below start at the **repository root**. Each subsection repeats its own `cd` so it
can be run independently.

### H.1 Operator benchmark (from `int8-lm-head/vec4`)

```bash
cd /path/to/llm-serving-performance-lab/int8-lm-head/vec4

export CUDA_VISIBLE_DEVICES=0
export INT8_ARTIFACT=/absolute/path/to/lm_head_int8_rowwise.safetensors
export QWEN_LM_HEAD_SHARD=/absolute/path/to/model-00004-of-00004.safetensors  # optional; required for the BF16 baseline

python operator/final_bench.py \
  --artifact "$INT8_ARTIFACT" \
  --bf16-shard "$QWEN_LM_HEAD_SHARD" \
  --out ./operator/run
```

Path notes:

- `python operator/final_bench.py` must be launched with `int8-lm-head/vec4` as the working
  directory, because the script path is relative to that directory.
- `final_bench.py` resolves its C++/CUDA probe sources relative to its own `operator/` directory,
  not relative to the shell's working directory.
- `--out` is resolved relative to the shell's working directory; the example writes to
  `int8-lm-head/vec4/operator/run/`. That path is git-ignored.
- Without `--bf16-shard`, the script produces only V2 and vec4 timings; it cannot produce the
  BF16/vec4 **2.159×** comparison.
- The run requires `CUDA_VISIBLE_DEVICES=0` and an RTX 3090. The script builds the probe with
  `torch.utils.cpp_extension.load`; it does not use a prebuilt binary.
- Output includes `final_bench_results.json` under `--out`. The script writes new results; it does
  not regenerate the frozen `operator/final_bench_results.json` in this directory.

### H.2 Serving plugin and 32-request ABBA (from `int8-lm-head/vec4/serving`)

Run the CUDA-extension build first, then install the plugin in editable mode, then run the ABBA
runner:

```bash
cd /path/to/llm-serving-performance-lab/int8-lm-head/vec4/serving

export QWEN_MODEL_DIR=/absolute/path/to/Qwen3-VL-8B-Instruct
export INT8_LM_HEAD_ARTIFACT=/absolute/path/to/lm_head_int8_rowwise.safetensors

python build_ext.py
python -m pip install -e .

# Import/metadata checks (do not start vLLM yet)
python - <<'PY'
import importlib.metadata as md
from pathlib import Path
import vec4_vllm_plugin

print("plugin file:", vec4_vllm_plugin.__file__)
print("default artifact:", vec4_vllm_plugin.DEFAULT_ARTIFACT)
print("entry points:", [ep for ep in md.entry_points(group="vllm.general_plugins")
                         if ep.name == "qwen_int8_vec4_head"])
build = Path(vec4_vllm_plugin.__file__).resolve().parent / "build"
print("extension files:", sorted(p.name for p in build.glob("int8_gemv_vec4_serving_ext*.so")))
PY

python scripts/run_vec4_serving_abba.py
```

Path and packaging notes:

- `build_ext.py` writes the extension into
  `int8-lm-head/vec4/serving/build/` and prints the resulting module path.
- `vec4_vllm_plugin.py` inserts that same `serving/build/` directory into `sys.path` before
  importing `int8_gemv_vec4_serving_ext`.
- **Use the editable install.** A non-editable `pip install .` copies `vec4_vllm_plugin.py` into
  `site-packages/`; its `Path(__file__).parent / "build"` and
  `Path(__file__).parent / "artifacts"` lookups then point into the wrong directory.
- The `vllm.general_plugins` entry point is
  `qwen_int8_vec4_head = vec4_vllm_plugin:register`; the runner sets
  `VLLM_PLUGINS=qwen_int8_vec4_head`.
- `INT8_LM_HEAD_ARTIFACT` overrides the plugin's default artifact path. The default is
  `serving/artifacts/lm_head_int8_rowwise.safetensors`; the artifact is not shipped.
- The runner requires port `8002` to be free, starts `vllm serve` itself, and writes its outputs
  under `serving/results/vec4_serving_abba_<timestamp>/` (git-ignored). It expects vLLM 0.28.0,
  `requests`, the built extension, and the installed plugin.
- This is a serving experiment, not a unit test. It will start a GPU server and generate real
  measurements only when the model and artifact are present.

### H.7 Limitations

- Operator result: single fixed shape, single GPU, synthetic activation, not whole-model.
- Serving result: 32 measured requests, ABBA, client approximate TPOT, descriptive only; no
  significance test was performed.
- BF16 A1→A2 drift is ≈3.61%; thermal/clock drift is not fully eliminated.
- CUDA Graph + `torch.compile` are part of the serving path; the kernel's isolated contribution
  is not separated.
- Correctness in `final_bench_results.json` compares V2 vs vec4, not full BF16-vs-INT8 quality.
- No memory savings: BF16 LM Head remains resident; INT8 is an additional copy.
- No claim of lossless quantization.
- No upstream vLLM merge.
- No multi-GPU, tensor-parallel, multi-node, NCCL, or RDMA claims.
