1. Research Question
============================================================

Why does MBT4096 become more beneficial than MBT2048 at high
concurrency for the exact-2048 -> exact-128 serving workload?

5. Condition A: C1 Decode Marker
============================================================

Profiled client TPOT:
28.519 ms/token

gemv2T:
instances = 128
start-to-start intervals = 127
mean interval = 28.918 ms
median interval = 28.315 ms

Interpretation:

Under the C1 execution regime, consecutive gemv2T launch
spacing closely tracks client-observed TPOT.

This establishes gemv2T as a useful empirical decode-step
marker for this C1 trace.

It does NOT establish a universal one-kernel-per-token rule.

============================================================
6. Concurrency Changes Kernel Regime
============================================================

At C1:
gemv2T is a dominant decode-region kernel family.

At C8:
gemv2T mostly disappears and 64x64 BF16 GEMM becomes a useful
decode-region timing marker.

Therefore kernel selection changes with batch/concurrency shape.

A different kernel pattern proves a changed execution regime,
not the exact bottleneck by itself.

============================================================
9. Hypothesis Status
============================================================

H1:
At C1, MBT effect should be small.

STATUS:
NOT DIRECTLY TESTED BY EXP12 PROFILING.

Exp08 serving data supports the behavioral observation, but
Exp12 did not profile C1 x MBT4096.


H2:
At C8, MBT2048 should exhibit more fragmented prefill execution
than MBT4096.

STATUS:
SUPPORTED.

Evidence:
prepare_prefill events = 9 vs 5.


H3:
At C8, MBT4096 should reduce prefill fragmentation and allow an
earlier transition into stable decode-dominant execution.

STATUS:
SUPPORTED.

Evidence:
final prepare_prefill marker approximately 655.7 ms earlier.


H4:
If MBT4096 improves TPOT by making steady-state decode faster,
its decode-step spacing should be tighter than MBT2048.

STATUS:
NOT SUPPORTED / FALSIFIED FOR THIS TRACE.

Evidence:
34.200 ms vs 34.412 ms steady-state 64x64 spacing.

============================================================
10. Main Mechanism Conclusion
============================================================

At high concurrency, the benefit of a larger scheduler token
budget is primarily associated with reduced prefill
fragmentation and reduced prefill/decode phase interference,
rather than faster steady-state decode execution.

This is a mechanism interpretation supported jointly by:

1. Exp08 formal serving behavior;
2. Exp12 Nsight Systems execution traces;
3. reduced prepare_prefill fragmentation;
4. nearly unchanged steady-state decode spacing.

============================================================
11. Important Boundaries
============================================================

- Profiler timing does not replace formal serving benchmark
  timing.

- Kernel instance counts do not directly equal token counts or
  scheduler-wave counts.

- CUDA API host time is not GPU kernel execution time.

- Kernel selection changes with batch shape.

- The mechanism conclusion applies to the tested workload and
  configuration. It is not a universal vLLM property.

- The stale "Exp07" display label in the reused burst client is
  a presentation/provenance label issue only. Raw logs are
